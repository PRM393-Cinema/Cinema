Abstract—Mobile cinema booking must coordinate local screen
state with server-owned reservations while users leave the ap-
plication for payment and later return. CosmoQ Cinema ad-
dresses this workﬂow with a Flutter customer application and
a shared ASP .NET Core 8 backend behind a Y ARP gateway.
This report examines the mobile implementation using startup
code, navigation, remote repositories, HTTP adapters, platform
conﬁguration, SQL, and tests. The client uses explicit session noti-
ﬁcations, secure-storage calls, coordinated refresh-token renewal,
movie/showtime discovery, periodically updated seat maps, book-
ing history, and QR ticket presentation. The backend uses Entity
Framework Core and Npgsql with PostgreSQL, server-priced
ten-minute holds, PayOS veriﬁcation, and RabbitMQ-mediated
notiﬁcation and refund processing. Mobile-speciﬁc paths include
external checkout, application-resumption veriﬁcation, ticket
sharing, calendar URLs, and staff QR-scanner integration. The
analysis distinguishes these source implementations from suc-
cessful physical-device execution. Seventeen isolated booking-
service tests and twenty-one gateway tests passed; backend builds
succeeded with four MovieService nullable warnings. The Flutter
suite passed 209 tests, with one informational analysis lint.
Docker-backed integration was blocked, and native release, live
merchant payment, and device acceptance were not executed.
The report contributes an evidence-linked description of mobile
state recovery and booking coordination without treating plugin
dependencies, test doubles, or platform folders as proof of
operational completion.
Index Terms —Mobile ticket booking, Flutter, Dart, ASP .NET
Core, JWT, PostgreSQL, PayOS, QR tickets.
I. I NTRODUCTION
Mobile cinema booking brings discovery, seat choice, pay-
ment, and ticket access into a small-screen interaction. The
user may leave the application to pay, return after the operating
system pauses it, or revisit a booking after a network failure.
A client must preserve an understandable distinction between
local selection, a server-held reservation, and a paid ticket.
CosmoQ Cinema addresses these tasks through a Flutter
customer application connected to a shared ASP .NET Core
backend [ 1], [ 2].
This paper focuses on the mobile build of the customer
entry point in Cinema_Mobile. The repository also builds
browser applications, but their management workspace is not
a principal topic here. Platform directories exist for Android
and iOS, as well as desktop targets; directory presence is not
evidence that every platform has been built, signed, deployed,
or tested. The veriﬁed source supports discussing a cross-
platform implementation while retaining those distinctions.
The mobile implementation integrates three principal engi-
neering mechanisms:
• Recoverable client state. Route-driven screens, remote
catalog data, secure-storage calls, and coordinated re-
newal support the customer session.
• Server-owned booking state. Seat availability, transac-
tional holds, order pricing, and payment reconciliation
remain backend responsibilities.
• Mobile ticket interaction. External checkout and re-
sumption, booking history, QR presentation, sharing, and
a staff check-in path complete the ﬂow.
Notiﬁcation read state, promotions, points, and reviews extend
these workﬂows. The contribution is their implementation and
integration, rather than a novel framework or a measured
improvement over another cinema application.

II. S YSTEM ARCHITECTURE OVERVIEW
A. Mobile-to-Service Topology
The mobile application uses the same public API gateway
as the other client builds. It serializes requests as JSON and
adds a bearer token for protected operations. The gateway
forwards requests to AuthService, MovieService, or Book-
ingService. Backend dependencies include PostgreSQL and
RabbitMQ; external communication includes PayOS HTTP
calls and SMTP email. Figure 1 shows these boundaries from
the mobile customer’s perspective [ 1], [ 3], [ 4].
There are three domain-service executables plus the gate-
way. MovieService also contains showtime and room code;
BookingService contains payment and notiﬁcation code. These
modules are not separate deployed services merely because
they have their own classes or database contexts. The gateway
and services are individually deﬁned in Docker Compose,
which provides a local service-based topology rather than
evidence of an operational cloud platform.
B. V eriﬁed Technology Stack
Table I distinguishes client, backend, and integration tech-
nology. The client uses Material widgets and Dart’s asyn-
chronous futures; no active Bloc or Riverpod implementation
was needed to explain its state ﬂow. Flutter’s architecture
documentation is relevant context [ 5], but the classes ac-
tually instantiated by AppDependencies.remote deter-
mine CosmoQ’s behavior [ 1].
The locally installed SDK reports Flutter 3.47.2 and Dart
3.13.2, matching the manifest’s Dart range. CI requests Flutter
3.47.4. Backend targets are .NET 8 and the review host uses
.NET SDK 9.0.305. These version facts describe the review
and conﬁguration; they do not assert a version for a published
mobile release [ 1], [ 6].
C. Conﬁguration and Data Flow
ApiConfig defaults Android’s emulator connection
to http://10.0.2.2:5000; other default targets
use localhost. A physical phone requires an appropriate
API_BASE_URL build deﬁnition and network access to the
gateway. A payment return URL can also be overridden.
Defaults for local development should not be read as HTTPS
deployment evidence [ 1], [ 4].
The UI calls repository interfaces, whose remote imple-
mentations invoke service adapters and a shared HTTP client.
JSON models hold movies, showtimes, seats, bookings, pay-
ments, notiﬁcations, and authentication data. The repositories
combine data when a screen requires more than one backend
resource: seat layout comes from MovieService and occupied
IDs from BookingService. This is client-side composition of
server results, not direct database access.
III. B ACKEND DESIGN AND IMPLEMENTATION
A. Identity as a Mobile Session Dependency
AuthService supports email registration and OTP veriﬁca-
tion, login, refresh, logout, password recovery, and proﬁle/-
password changes. BCrypt hashes passwords and OTP values;
JWTs carry the user’s identity and role claims. JWT signing
is HMAC-SHA256. The refresh ﬂow revokes an accepted
old refresh token before returning new session credentials.
Tokens originate in this service rather than in a social-login
or federated identity provider [ 7].
For the phone, the useful contract is an authentication
response followed by authenticated API requests and recovery
from expiry. Issuer, audience, signature, and lifetime checks
occur in gateway/service JWT validation. Gateway middleware
also requests current account status for protected requests.
A locked account or changed roles can therefore invalidate
continued use through the gateway even while a token’s
timestamp is still valid. An unreachable status service results in
503, which the mobile client must present as a service failure
rather than a successful action [ 3], [ 8].
B. Catalog and Seat Information
MovieService supplies browsing, details, genres, and show-
time selection. The showtime implementation checks that
selected seats belong to the showtime’s room, the show is
open, and its start time is still in the future. Sweetbox seats
are validated as pairs when the partner is deﬁned. These checks
run server-side independently of the phone’s selection widgets
[9].
Seat pricing uses a format surcharge followed by a type
surcharge. Normal, VIP , and sweetbox values are deﬁned
in helpers; the resulting seat prices are returned in server
responses and reobtained for booking creation. The mobile
display helps the user understand a total, while the backend
supplies the authoritative amount. This limits trust in stale or
manipulated client inputs without asserting that every possible
pricing scenario was device-tested.

menu, resolves promotions, and applies permitted loyalty

D. Database Design for Mobile Workﬂows
SQL initialization creates six databases on the conﬁgured
PostgreSQL 17 instance. Auth data uses users, roles, a join
table, refresh tokens, and OTPs. Movie data is separate from
rooms, seats, and showtimes. Booking data includes seat snap-
shots, reservations, concessions, promotions, loyalty records,
and reviews. Payment and notiﬁcation records have separate
contexts/databases. The Npgsql EF Core provider connects
these models to PostgreSQL [ 2], [ 10], [ 12].
The selected ERD in Fig. 2 distinguishes SQL foreign keys
from logical ID references. Rooms have declared seat/show-
time relationships; bookings have declared booking-seat re-
lationships; refunds reference payments. Cross-database user,
movie, and booking IDs are application references rather than
SQL-enforced relationships. The reservation’s booking ID is
not declared as a foreign key in the inspected base schema. A
full mobile workﬂow therefore depends on service validation
and event processing as well as local constraints.
Schema ﬁles and migrations are maintained in the ini-
tialized database submodule, with additional backend SQL
updates. The Compose initialization and migration jobs mount
these sources. Inspection veriﬁes intended schema structure

E. Payment and Asynchronous F ollow-Up
PayOS integration requests checkout links and queries
payment status. Creation includes merchant headers and an
HMAC signature. The webhook path validates the payload sig-
nature before trusting ﬁelds and checks order/amount against
the saved payment. A veriﬁed provider status can also trigger
reconciliation when the customer returns to the app. These
source paths avoid equating an external-browser launch with
payment success [ 2], [ 13].
Payment and booking records are not described as one
distributed transaction. The code contains a conﬁrmation-or-
refund path when payment succeeds after the booking can
no longer be conﬁrmed. Staff record refund processing and
transfer references; automatic bank refund execution was not
found. RabbitMQ outbox workers publish persistent events
after local commits, and consumers process notiﬁcation/refund
and showtime-cancellation effects. Publisher conﬁrms and
event-ID deduplication support retries but do not establish
exactly-once external email delivery [ 2], [ 14].

wide Bloc or Redux architecture [ 1].

Visible session recovery. Network errors can preserve

C. UI Composition and Feedback
Feature directories group authentication, movie, seat, book-
ing, payment, notiﬁcation, proﬁle, and staff screens. Shared
theme ﬁles deﬁne spacing, typography, color, and radius
values. Reusable buttons, panels, loading, empty, and error
states keep common interactions consistent. Screen code uses
asynchronous calls, mounted checks, and busy ﬂags to avoid
updating disposed widgets or repeatedly submitting an active
action [ 1], [ 15].
The layout switches desktop navigation at 900 logical pix-
els, while phone layouts use the narrow application frame. Seat
maps and reusable column components respond to available
width rather than assuming a ﬁxed desktop canvas. The
existence of phone-sized widget assertions supports testing
those layouts with ﬁxtures; it is not a general accessibility,
device-compatibility, or performance certiﬁcation.
D. Platform-Speciﬁc Actions
Platform actions are isolated from the shared booking
contract [ 1]:
• External activities. Native trailers and PayOS checkout
launch through url_launcher; the native trailer path
does not embed the Web player.
• Sharing and calendar links. share_plus invokes
sharing, with a clipboard fallback. Calendar support con-

• Ticket display and scanning. qr_flutter ren-

The iOS property list declares a camera-purpose description
and Android declares Internet access. These settings show
platform intent; camera permissions, release packaging, and
physical-device scanning remain unveriﬁed.
V. C ORE BUSINESS WORKFLOWS
A. Authentication and Account Use
A customer may browse as a guest, but protected book-
ing/account actions require sign-in. Registration sends account
data to AuthService and continues through email OTP veri-
ﬁcation. Password recovery and proﬁle editing have remote
service paths. Session restoration reads saved credentials and
current-user information; failures requiring authentication re-
turn the user to sign-in. The application does not establish
biometric login merely by depending on a package that can
support biometric options [ 1], [ 7].
B. Discovery, Showtimes, and Seat Choice
Home browsing combines now-showing/coming-soon se-
lection, genres, and title search, with a 350-millisecond de-
bounce. Details expose metadata, trailer actions, reviews,
and open showtimes. The catalog repository fetches sched-
ules within a seven-day customer window. Once a show
is chosen, room seats and occupied IDs are combined into
ShowtimeSeatsData [1].
Local choice and server hold. The selected seat set remains
local until order submission. A ﬁve-second timer refreshes the
visible map; conﬂicting local seats are removed, with sweetbox
partner handling. Failed refreshes retain the last map and
retry on a later tick. The booking transaction is consequently
essential even when the display recently looked current. This
is periodically refreshed availability, not veriﬁed WebSocket
or SignalR push [ 1], [ 2].

C. Order Calculation
Summary collects seats, concessions, promotion choice, and
requested member points before submission. The backend
recalculates the total. If S is seat value, D the applicable ticket
promotion, C concessions, and q redeemed points, the code
implements
T = S − D + C − 1000q. (1)
The redemption ceiling is 50% of the pre-points total and the
account’s available balance. Promotion reductions are capped
and rounded down to 1,000-VND steps. This notation explains
real arithmetic rather than adding an unrelated optimization
model [ 2].
Loyalty earning is also explicit. For paid amount A and
tier earn rate r, the helper returns ⌊Ar/1000⌋ points. The
conﬁgured tier rates are 5%, 7%, and 10% for MEMBER, VIP ,
and VVIP . These values describe code constants; no customer-
retention or revenue effect has been measured.
D. External Checkout and App Resumption
Figure 3 describes the mobile checkout path. After creation
of a pending booking, the app requests a PayOS link and
launches it externally. PaymentScreen observes application
lifecycle changes: a resumed app that previously opened
checkout requests veriﬁcation. It also polls booking state every
ﬁve seconds, with provider veriﬁcation every sixth eligible
poll, and disposes timers when leaving the screen [ 1].
Resumption and reconciliation. The displayed countdown
is computed from the booking expiry; it does not authorize
or extend the hold. A successful provider result is reconciled
on the backend before a conﬁrmed ticket is shown. If the
application is terminated, booking history and ID-based detail
loading provide a recovery path; no claim is made that the OS
automatically returns to the exact prior payment screen or that
ofﬂine purchase completion is supported.

VI. S ECURITY AND DATA PROTECTION
A. Token and Account Protection
Protection is divided between client persistence and API
enforcement:
• Local credentials. SecureAuthTokenStorage per-
sists tokens, expiry, and user data using serialized writes
and clears unreadable storage. Platform-speciﬁc package
implementations are used [ 1], [16]; hardware backing and
compromised-device resistance were not tested.
• Server enforcement. Password/OTP hashing, input vali-
dation, role checks, and resource ownership constrain API
use. Customer identity comes from claims and pricing
uses backend data [ 2], [ 7].
• Gateway controls. Rate limiting and current-account
validation add request checks independently of the mobile
screen state [ 3].
No additional biometric gate, certiﬁcate pinning, or device at-
testation was established. These mechanisms do not constitute
a complete security guarantee.

The evidence supports an implemented remote-client archi-

security level. A workﬂow with both UI code and API code is
reported as implemented in source with runtime veriﬁcation
outstanding where appropriate. No ﬁxture data or example
payment record is counted as a successful real customer action.
VIII. L IMITATIONS AND FUTURE DEVELOPMENT
A. Current Limitations
The client depends on connectivity for catalog retrieval,
booking, and payment conﬁrmation. A stale seat map is
possible between polling ticks or after a failed refresh. External
checkout introduces operating-system lifecycle and browser
behavior that widget mocks cannot fully reproduce. The im-
plementation does not establish ofﬂine booking, native push,
universal app links, or biometric authentication merely through
route names or dependencies [ 1].
Refund transfer remains manual staff work. Email sending
and database updates are separate operations despite event-
ID checks, so exactly-once SMTP delivery is not guaranteed.
Local-time timestamps with Npgsql legacy behavior constrain
assumptions about users in other time zones. The source
includes a calendar duration fallback of 150 minutes when
exact showtime data cannot be obtained; that fallback is a
convenience, not guaranteed schedule accuracy [ 1], [ 2], [ 4].
The review could not demonstrate live provider operation,
container integration, native secure storage, QR scanning, or
signed store distribution. Existing SQL seed payment labels
are demonstration data, not evidence of active VNPA Y or
MOMO implementations. Platform folders establish potential
targets rather than a tested support matrix. These limits prevent
describing the application as production-ready.
B. Recommendations
Recommended next steps are a controlled Android/iOS de-
vice matrix, release build and permission checks, and lifecycle
tests that interrupt checkout at multiple stages. V eriﬁcation
should include token restoration after process death, network
transitions, camera denial, share-sheet failure, and repeated
payment reconciliation. Container suites and schema migra-
tions should be run before a complete system acceptance test.
Further recommendations include validating HTTPS and
release network policy, testing accessibility and text scaling,
resolving backend nullable warnings, and reviewing notiﬁca-
tion delivery requirements before considering native push. Any
push, ofﬂine cache, biometric gate, or deep-link enhancement
should be treated as proposed development rather than an
implemented feature or committed project roadmap.
IX. C ONCLUSION
CosmoQ’s mobile implementation provides a Flutter cus-
tomer workﬂow over a shared ASP .NET Core backend.
Session recovery, remote repositories, periodic seat updates,
server-created holds, external checkout reconciliation, and QR
ticket access form the central implementation. SQL constraints
and backend authorization carry responsibilities that cannot
safely be delegated to phone UI state. The reported veriﬁcation
establishes selected compilation and automated-test outcomes
while preserving the gap to physical-device and live provider
validation. The system is therefore documented as an im-
plemented mobile client with explicit operational veriﬁcation
limits.
