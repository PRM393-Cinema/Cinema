Abstract—Cinema ticketing requires customer purchases and
cinema operations to agree on showtimes, seat ownership, and
payment state. CosmoQ Cinema implements these interactions
through Flutter Web customer and administration entry points
and a shared ASP .NET Core 8 backend. This report reconstructs
the implementation from source, dependency manifests, SQL
schemas, tests, and deployment scripts. A Y ARP gateway routes
JSON requests to authentication, movie, and booking services.
Entity Framework Core with Npgsql accesses six PostgreSQL
databases; transactional reservation rows and a seat/showtime
uniqueness constraint support seat contention handling. The
browser layer uses named routes, explicit session state, remote
repositories, responsive layouts, and token-refresh coordination.
PayOS checkout and reconciliation, RabbitMQ outboxes, notiﬁ-
cation records, counter sales, promotions, and loyalty functions
are analyzed within their veriﬁed boundaries. Seventeen isolated
booking-service unit tests and twenty-one gateway tests passed;
backend compilation succeeded, with four nullable warnings in
MovieService. Container-dependent veriﬁcation was blocked by
an unavailable Docker daemon. The Flutter suite passed 209
tests; both browser entry points compiled, and analysis retained
one informational lint. These checks remain separate from source
implementation, and no live payment or production deployment
is claimed. The contribution is a traceable account of the Web
system’s coordination mechanisms and remaining veriﬁcation
obligations.
Index Terms—Cinema booking, Flutter Web, ASP .NET Core,
PostgreSQL, JWT, PayOS, RabbitMQ, cinema management.
I. I NTRODUCTION
Cinema ticketing couples a customer-facing purchase with
operational tasks such as maintaining schedules, allocating
seats, collecting payments, and admitting customers. A book-
ing interface must therefore coordinate information that can
change between browsing a show and completing checkout.
A seat visible as free is not necessarily still available when a
customer submits an order. Likewise, a browser returning from
a payment page is not sufﬁcient evidence that the cinema has
received money. These are the concrete coordination problems
addressed by the inspected CosmoQ implementation, rather
than measured claims about the shortcomings of a particular
cinema’s previous process.
CosmoQ Cinema implements customer booking and
cinema-management workﬂows through Flutter browser ap-
plications and an ASP .NET Core backend. This paper ex-
amines the Web system: the customer application built from
main.dart and the administration application built from
main_admin.dart. They are distinct entry points in one
Flutter source project, not independently veriﬁed frontend
repositories. A mobile build shares customer code and backend
APIs, but its platform behavior is outside the primary scope
of this paper. Repository evidence, including source-level de-
pendencies and SQL, establishes the implementation described
here [ 1]–[4].
The principal engineering contributions are the following
integrated mechanisms:
• Browser workﬂow composition. Named navigation, ses-
sion recovery, responsive customer pages, and role-aware
management entry points share remote API adapters.
• Server-controlled reservation. Backend pricing, trans-
actional seat holds, and a seat/showtime uniqueness con-
straint coordinate competing purchases.
• Payment and operational follow-up. Provider recon-
ciliation and outbox events connect booking state to
notiﬁcations, refunds, and cinema operations.
Concessions, promotions, loyalty balances, reviews, check-in,
and notiﬁcation records support these workﬂows. Their source
implementation does not establish a production deployment,
successful live payment, or performance improvement over
another ticketing system.

II. S YSTEM ARCHITECTURE OVERVIEW
A. Deployment Units and Communication
Figure 1 summarizes the veriﬁed Web topology. Browser
requests use JSON over HTTP through a Y ARP gateway.
AuthService manages identity; MovieService contains movie
and showtime/room functionality; BookingService contains
booking, payment, notiﬁcation, and related business services.
Each is an ASP .NET Core executable. Their separate Compose
service deﬁnitions and inter-service HTTP/event communica-
tion support describing the backend as a service-based deploy-
ment. This does not imply independently scalable production
infrastructure or a separate service for every business module
[3], [ 5]–[7].
The gateway listens on host port 5000 in Compose. Back-
end and infrastructure debug ports are generally bound to
loopback, while the gateway is accessible from the network.
Route-to-cluster conﬁguration selects the destination service;
downstream failures are translated into structured 503 or 504
responses. BookingService calls MovieService for authorita-
tive showtime and seat data, forwarding the acting user’s
bearer token. RabbitMQ carries business events after local
transactions commit. Browser clients do not connect directly
to PostgreSQL or RabbitMQ [ 3], [ 5], [ 7].

C. Persistence Boundaries
Compose initializes six databases on one PostgreSQL in-
stance. Their domain sufﬁxes are auth, movie, showtime,
booking, payment, and notification; full names fol-
low the cinema_..._db convention. MovieService owns
two EF contexts and BookingService owns three. Thus six
database names do not imply six backend executables. Npgsql
supplies the EF Core provider [ 9]; source registration selects
each database [ 3], [ 6], [ 7], [ 10].
III. B ACKEND DESIGN AND IMPLEMENTATION
A. Identity and Access Services
Account lifecycle. AuthService implements registration,
email veriﬁcation, login, refresh, logout, proﬁle changes, pass-
word changes, and administrative account operations. Pass-
words and OTP values are hashed with BCrypt. JWT genera-
tion uses HMAC-SHA256 and includes user identity and role
claims. Refresh tokens are generated from 64 cryptographi-
cally random bytes, stored in the authentication database, and
revoked when rotated. A logout revokes the supplied refresh
token; it is not described here as an instantaneous blacklist of
every previously issued access token [ 10].
Request authorization. JWT validation checks issuer, au-
dience, signature, and lifetime. Gateway policies and down-
stream controller policies restrict privileged actions. Protected
gateway requests also query AuthService’s current-account
endpoint. Disabled accounts are refused, and a mismatch
between current roles and token roles returns a role-change
error. Failure to perform that check returns 503 rather than
forwarding an unchecked protected request [ 5]. These are con-
crete bearer-token mechanisms consistent with the ASP .NET
Core model [ 11], not a claim of OAuth/OpenID Connect
federation.
B. Catalog and Schedule Support
MovieService provides movie browsing, detail retrieval,
genres, title search, and administrative editing. Its showtime
code validates room membership of requested seats, rejects
shows that are not open or have started, and enforces paired
sweetbox selection when a partner exists. Seat prices derive
from the showtime price, presentation-format surcharge, and
seat-type surcharge. Room, seat, and schedule APIs support

C. Booking Transactions and Seat Contention
The booking controller derives the customer ID and email
from authenticated claims for self-service purchases. The
service rejects duplicate seat IDs, requests server-side seat
prices, and calculates concessions from the active menu. It
loads showtime timing for later cancellation policy decisions.
The movie title normally comes from MovieService, although
the code retains a request-title fallback if no title is returned;
therefore it would be inaccurate to claim that every display
ﬁeld is exclusively server-derived [ 7].
The transaction uses three complementary mechanisms [ 4],
[7], [ 12]:
• Lock existing reservations. PostgreSQL FOR UPDATE
locks the selected rows; booked seats and unexpired holds
are rejected.
• Constrain new reservations. The unique uq_seat_
per_showtime key protects a seat/showtime pair be-
fore a row exists to lock. A unique violation rolls back
the transaction and returns a conﬂict.
• Commit related state. The booking, seat snapshots,
holds, and outbox event are persisted in one local trans-
action.
These are speciﬁc concurrency mechanisms; they do not
establish an unrestricted guarantee under every failure mode.

browser sessions can submit the same selection despite a

D. Database Model and Relationships
Figure 2 shows a selected, veriﬁed relational subset. Solid
edges represent declared SQL foreign keys; dashed edges
denote application-level ID references across database bound-
aries. Authentication uses users, roles, a join table, refresh
tokens, and OTP records. Showtime storage relates rooms to
seats and showtimes. Booking storage keeps ticket-seat price
snapshots and concession lines. Payments relate to refunds
within their own database [ 4], [ 7].
Cross-database references such as a payment’s booking ID
are not PostgreSQL foreign keys in the supplied schema.
The reservation’s booking ID is also not declared as an SQL
foreign key in the inspected base script. These distinctions
matter when discussing consistency: asynchronous handlers
and application checks coordinate business records, while
database constraints cover only their deﬁned local scope. The
ﬁgure is deliberately a partial ERD, not a claim to reproduce
every table or every entity-mapping detail.
Initialization SQL and incremental migrations are kept in
the database submodule. Compose mounts those ﬁles and runs
an initialization script for an empty volume, followed by a
migration job. Additional SQL under the backend tree updates
movie metadata and reviews. The migration script excludes
selected demo-seeding migrations. This inspected path uses
SQL scripts; no claim is made that EF migration history
governs the deployed schema [ 3], [ 4].
E. Payments and Event Delivery

and cancels links. It sends merchant headers and signs creation
payloads with HMAC-SHA256. Webhook handling validates
the data signature before using ﬁelds, matches the payment
order and amount, and records the successful payment. A
later booking-conﬁrmation conﬂict can initiate a refund re-
quest. These operations are integrated in source; live merchant
delivery was not exercised [ 7], [ 13].

lished events with FOR UPDATE SKIP LOCKED , publish
persistent messages with publisher conﬁrmations, and record

IV. W EB APPLICATION ARCHITECTURE AND
IMPLEMENTATION
A. Entry Points and Browser Navigation
Both entry points restore a stored session before construct-
ing their application. The customer router maps named paths to
movie, showtime, booking, payment, notiﬁcation, and account
screens. Authentication-required routes redirect to login while
retaining a pending destination. Detail routes accept an iden-
tiﬁer and can reload their data when no in-memory navigation
argument exists. This is particularly relevant to browser refresh
and shared links [ 1].
The administration router classiﬁes routes as public, staff,
or admin. It checks roles before creating protected pages.
This improves navigation but is not the security boundary:
the backend independently authorizes management operations.
CI deﬁnes a customer Web build and a separate admin build
using -base-href /admin/ . The conﬁgured build layout
is evidence of packaging, not proof that a hosting environment
serves both correctly [ 1], [ 15].
B. State and API Abstractions
SessionState extends ChangeNotifier; an
InheritedNotifier exposes authentication, the current
user, and unread notiﬁcation count. Screens otherwise
maintain local state for loading, selection, ﬁlters, and errors.
No evidence requires labeling this state system as Bloc,
Riverpod, or Redux. Repositories translate screen requests
into service calls; the shared API client handles JSON,
timeouts, bearer headers, and structured errors [ 1].

B. Pricing and Checkout
For ticket subtotal S, applicable promotion discount D,
concession subtotal C, and redeemed loyalty points q, the
booking code computes
T = S − D + C − 1000q. (1)
The loyalty helper restricts redemption to at most ⌊0.5(S −
D + C)/1000⌋ points, additionally bounded by the customer’s
balance. Promotion calculation caps the discount at 90% of
ticket value and rounds it down to a 1,000-VND increment.
These are implementation constants, not measured economic
outcomes [ 7].
Figure 3 summarizes checkout. The payment page opens
the returned PayOS URL and displays the booking’s expiry.
It polls booking state every ﬁve seconds and invokes provider
veriﬁcation every sixth eligible poll. Browser return parame-
ters identify an order to verify; the backend remains respon-
sible for deciding payment success. A timer or a successful
redirect alone does not conﬁrm the ticket [ 1], [ 7].
C. Conﬁrmation, Cancellation, and Operations
Conﬁrmed bookings expose history/detail views and QR
ticket content. Customers can request cancellation subject
to server policy; the default paid-booking cutoff is two
hours before the show. A customer refund request sets
REFUND_PENDING and retains seats until the refund de-
cision. Staff complete or reject refund processing through
privileged APIs. The code records manual transfer references;
it does not implement an automatic banking refund through a
PayOS refund endpoint [ 2], [ 7].
Staff workﬂows include counter booking, cash collection,
booking lookup, check-in, showtime operations, payment
records, and notiﬁcation handling. Admin screens additionally
manage movies, rooms, users, concessions, promotions, and
membership data. These are source-backed screen-to-service
paths, not a claim that every management path was manually
exercised. Check-in requires an eligible paid booking and a
server-conﬁgured time window; repeated admission is rejected
by business logic [ 2], [ 7].
VI. S ECURITY AND DATA PROTECTION
A. Trust Boundaries
The implementation places checks at three trust boundaries
[5], [ 7], [ 10]:
• Identity and ownership. Gateway/service authorization
accompanies UI routing. Booking reads check ownership;
self-service creation uses identity claims.
• Order value. Server pricing recalculates seat and con-
cession amounts instead of trusting totals submitted by
the browser.
• Provider data. Webhook signatures are checked before
payment data is used to conﬁrm a booking.
Password validation additionally accounts for BCrypt’s input-
length boundary.
B. Browser Storage and Conﬁguration
The client actively uses flutter_secure_storage for
access/refresh tokens and user metadata. Writes are sequential,
with a source comment explaining ﬁrst-write key creation on
Web. Unreadable storage clears local credentials. This estab-
lishes the chosen storage abstraction, not an application-level
guarantee against script execution or browser compromise. The
package documents HTTPS or localhost requirements for its
Web backend [ 1], [ 16].
Deployment conﬁguration. Gateway CORS uses conﬁg-
ured origins when present, but falls back to allowing any
origin if the list is empty. Fixed-window IP rate limits include
a separate authentication policy and return 429 responses.
Compose passes secrets via environment variables; the review
did not open or publish credential values. The supplied local
topology exposes HTTP , so TLS termination is a deployment
requirement to verify, not an observed property of a live
website. Seed accounts and demonstration data should not be
treated as a production identity baseline [ 3]–[5].

VIII. L IMITATIONS AND FUTURE DEVELOPMENT
A. Current Limitations
The two browser applications share a Flutter project, so
reports of independent Web and mobile products should not
imply independent source ownership. Runtime availability
depends on gateway, identity, data, and messaging services;
the account-status call adds a dependency on AuthService for
protected requests. Polling provides periodic updates rather
than immediate server push. Temporary refresh failures delib-
erately retain older availability, making the booking transaction
the ﬁnal arbiter [ 1], [ 5], [ 7].
Refund transfer is a staff operation. Notiﬁcation handling
records failed email sends for staff retry; database dedupli-
cation does not make SMTP and database persistence atomic.
Local-time timestamps and legacy Npgsql behavior are explic-
itly used, limiting claims about multi-time-zone deployment.
The base SQL includes demonstration payment method labels
such as VNPA Y and MOMO; no active integrations for those
providers were established by the inspected payment adapter.
Missing runtime evidence and compiler warnings further limit
claims of operational readiness [ 3], [ 4], [ 7].
B. Recommendations
Future work should ﬁrst execute the container suites and
migrations on a controlled environment, add live provider
acceptance checks with safe merchant test arrangements, and
verify browser reloads and payment returns under HTTPS.
Recommendations also include resolving nullable warnings,
validating CORS and secret settings for a named deployment,
and testing keyboard/screen-reader operation and supported
browser printing. A push-based availability channel could be
evaluated if polling becomes insufﬁcient; it is not a committed
roadmap item or a feature of the inspected version.
IX. C ONCLUSION
CosmoQ’s Web implementation combines Flutter customer
and administration entry points with a shared ASP .NET Core
service backend. Its most substantive mechanisms are source-
backed pricing and ownership checks, transactional seat holds,
payment veriﬁcation, and event-mediated notiﬁcation/refund
processing. SQL and entity mappings clarify both local con-
straints and cross-database consistency responsibilities. Suc-
cessful isolated backend checks substantiate speciﬁc imple-
mentation properties, while the reported runtime limitations
prevent broader claims about production security, live pay-
ments, or capacity. The resulting system is a documented
engineering implementation whose next evaluation step is
controlled end-to-end deployment veriﬁcation.
